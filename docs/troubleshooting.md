# 排错指南

[返回首页](../readme.md)

先确认当前出问题的是加载、连接、消息接收、指令执行还是发送。连接建立只说明 WebSocket 可用，不能代替消息和媒体验证。

## 插件无法启用

确认 Koishi 版本符合要求，已安装并启用 `@koishijs/plugin-server`。如果日志提示服务依赖缺失，先解决依赖，再启用适配器。
适配器必须安装在正在运行的 Koishi 应用中；安装到另一个目录不会被当前实例加载。

## 手机无法连接

1. 服务端是否打印了「手机 WeBridge 的『WebSocket 服务端地址』填」对应的地址提示。
2. 手机是否能访问该地址的主机和端口，防火墙、容器映射与域名解析是否正确。
3. 路径是否完整，包含最后一段密钥；不要使用电脑的 localhost，也不要添加 `/agent`。
4. WeBridge 是否选择 WebSocket，相关开关是否开启。
5. 使用 HTTPS 代理时，手机填写的是否为 `wss://`，证书是否有效，代理是否允许 WebSocket 升级。

「插件已连接，等待 hello」表示网络连接建立；「握手完成」表示设备握手完成。
出现「已有连接，关闭旧的」时，检查是否存在重复实例或重复连接，新连接会替换旧连接。

地址的最后一段是访问密钥，反馈时使用 `<已隐藏>` 替换，保留协议、主机类型及路由结构即可。

## 在线但没有回复

先用另一个账号发送一条文本，查看日志是否出现「收到消息」：

| 现象 | 优先检查 |
| --- | --- |
| 没有对应事件 | 设备接收回调、账号在线状态和连接 |
| 出现「丢弃迟到事件」 | 断线补发消息超过 `dropStaleEventSeconds`；按业务需要调整，不要仅为排错关闭过滤 |
| 出现「非文本消息/通知事件」 | 该内容可能是通知或未支持的类型；用普通文字重试 |
| 有「收到消息」但没有执行指令 | 业务插件是否启用、过滤器、Koishi `prefix`、用户权限和频道受理设置 |
| 有「发送失败」或「发送异常」 | 设备发送开关、权限、错误码、引用是否仍有效及设备端实际状态 |

用 `echo` 插件做最小验证，群聊同时尝试 `@机器人 echo 测试`。裸指令是否触发由 Koishi 配置决定，适配器不要求所有群消息必须 @。
前缀规则见 [Koishi 指令系统](https://koishi.chat/zh-CN/manual/usage/command)。

机器人自己发出的消息不会再次触发普通业务插件，以避免回复循环；开启归档后仍可记录设备回推的自发消息。

## 文字正常，媒体不可用

| 现象或原因 | 处理方向 |
| --- | --- |
| 代理返回 413 | 调整代理上传限制，需覆盖媒体大小与 multipart 开销 |
| 上传返回 404 | 检查是否代理了整个路由前缀，是否错误改写或去掉了路径 |
| `too-large` | 调整对应媒体上限，最大 32 MiB；语音还需考虑解码后的大小 |
| `timeout` / `media_timeout` | 检查手机取件、上传地址可达性和网络；适配器总等待最多 200 秒 |
| `message_not_found` | 设备已找不到该消息；用新收到的消息重试 |
| `unsupported_media_type` / `unsupported_voice_codec` | 设备不支持导出该类型或编码 |
| `disconnected` / `account_changed` | 重新连接当前账号后，用新消息验证 |
| `busy` 或队列已满 | 先降低并发与消息量，检查较早的媒体任务是否长时间等待 |

还要确认 `acceptMedia` 为 `true`，设备可以执行统一媒体取件 `upload_message_media`，且手机能够向 Koishi 的上传路由发起 HTTP POST。
出现「入站媒体已就绪」说明适配器已经取得内容；若业务插件仍无法识别，检查它是否读取标准媒体元素，以及是否支持 `data:` 内容。开启托管后，`src` 是 http(s) 而不是 `data:`。

发图片等出站媒体时，URL 必须能被手机下载，并直接返回文件内容。Koishi 主机本地路径、`data:` 地址和需额外登录的网页不能直接作为媒体来源。

| 现象或原因 | 处理方向 |
| --- | --- |
| 转发收到的媒体失败，或日志写着需要 http(s) | 确认 `inboundMediaRelay` 已开启并重新加载适配器。未开启时入站 `src` 仍是 `data:`，出站会跳过 |
| 日志出现「入站媒体未托管」且 `reason=capacity` 或 `too-large` | 这一条仍以 `data:` 投递。提高条数或总字节上限，或等现有条目过期；不会挤掉未过期的托管 |
| 托管地址返回 404 | 已超过 `inboundMediaRelayTtl`、令牌不对，或适配器已卸载。过期不会续期 |
| 本机能打开托管地址，手机下载失败 | 地址主机与 WebSocket 相同。反向代理要放行 `GET /webridge/media/relay/`，不要只代理 WebSocket 那一条路径 |

路径令牌就是下载凭证。反向代理若记录完整 URI，日志里会留下这个凭证；请缩短访问日志保留时间，或不要记录该路径。适配器自己的日志不打印令牌和完整托管地址。

## 昵称仍然显示账号 ID

群消息会按需查询成员目录。目录查询失败、资料缺失、首次等待超时或 `directoryTimeout` 为 `0` 时，可能暂时回退账号 ID。
先检查设备能否正常查询群成员，再检查 `bot.getGuildMember()` 返回值。群名片读取 `session.event.member.nick`；`session.username` 还受 Koishi 用户名称影响。

## 发送成功却没有消息 ID

文本命令回执不直接提供可撤回的消息 ID，适配器需要在 `echoTimeout` 内可靠匹配自发回推。
等待超时、断线、重复正文无法区分或设备改写正文时，`bot.sendMessage()` 可能返回空数组；这不能单独判定发送失败。
媒体发送不返回可用于撤回的 ID。撤回和引用还受设备近期消息缓存及微信端实际限制影响。

## 归档没有记录

确认 `archive.enabled` 已开启、数据库服务可用、消息处于 `archive.filter` 和适配器配置的作用范围中。
具备权限的管理账号可执行 `归档.状态`，查看成功、失败、丢弃及目录刷新计数。
没有数据库时，消息收发和通讯录仍可使用，但不会归档；详见 [通讯录与归档](../ARCHIVE.md)。

## 提供问题信息

请附上适配器与 Koishi 版本、部署方式、出现问题的步骤、预期与实际结果，以及对应时间段的脱敏日志。
隐藏连接密钥、账号标识和聊天内容；媒体问题同时说明文件类型、大小与错误原因。
